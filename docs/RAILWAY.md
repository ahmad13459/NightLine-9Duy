# استقرار روی Railway — راهنمای دقیق

## چه چیزی ریلوی به شما می‌دهد

| متغیر | چه زمانی | مقدار نمونه |
| :--- | :--- | :--- |
| `PORT` | همیشه | `8080` |
| `RAILWAY_PUBLIC_DOMAIN` | بعد از ساخت دامنه | `nightline-production.up.railway.app` |
| `RAILWAY_TCP_PROXY_DOMAIN` | بعد از ساخت TCP Proxy | `roundhouse.proxy.rlwy.net` |
| `RAILWAY_TCP_PROXY_PORT` | بعد از ساخت TCP Proxy | `11105` |
| `RAILWAY_TCP_APPLICATION_PORT` | بعد از ساخت TCP Proxy | `8443` |
| `RAILWAY_VOLUME_MOUNT_PATH` | بعد از اتصال Volume | `/data` |
| `RAILWAY_REPLICA_REGION` | همیشه | `us-west2` |

پنل همهٔ این‌ها را خودکار می‌خواند؛ هیچ مقداری را لازم نیست دستی کپی کنید. اگر خواستید، در **تنظیمات** می‌توانید override کنید.

## چک‌لیست راه‌اندازی

1. **Deploy from GitHub** → مخزن را وصل کنید. بیلد با `Dockerfile` انجام می‌شود و سه باینری را دانلود می‌کند (حدود ۲ دقیقه).
2. **Generate Domain** برای HTTPS.
3. **TCP Proxy → Target Port 8443**. (اگر پورت دیگری دادید، `NL_TCP_PORT` را همان بگذارید.)
4. **Volume → Mount Path `/data`**.
5. باز کردن `https://<domain>/setup` و ساخت حساب مدیر.
6. تب **پروتکل‌ها** → روشن کردن روش‌های دلخواه.
7. تب **تلگرام** → روشن کردن MTProto/SOCKS/HTTP.
8. تب **کاربران** → ساخت کاربر → لینک اشتراک یا QR.

## مصرف منابع

| فرآیند | رم تقریبی |
| :--- | :--- |
| Node (پنل + مالتی‌پلکسر) | ۴۵–۷۰ مگابایت |
| Xray-core | ۳۵–۶۰ مگابایت |
| sing-box | ۳۰–۵۰ مگابایت |
| mtg | ۱۰–۲۰ مگابایت |

در پلن رایگان (۰٫۵ گیگ) هر چهار مورد جا می‌شود، اما:
- اگر از sing-box استفاده نمی‌کنید، از **تنظیمات → هسته‌ها** خاموشش کنید (یا گزینهٔ «فقط وقتی اینباند دارد» را روشن بگذارید).
- تعداد اینباندهای فعال را کم نگه دارید؛ هر اینباند یک listener و حافظهٔ کوچک است.
- لاگ را روی `warning` نگه دارید.

## پایداری داده

بدون Volume، مسیر داده `/data` موقتی است و با هر دیپلوی پاک می‌شود. با Volume:
- `nightline.json` (کاربران، اینباندها، سکرت‌ها، تنظیمات)
- `state/xray.json` و `state/sing-box.json` (کانفیگ تولیدشده)
- `state/reality.json` و `state/certs/*` (کلید REALITY و گواهی خودامضا)
- `logs/*.log`

## دیپلوی مجدد و ارتقا

1. از **تنظیمات → دریافت پشتیبان** یک JSON بگیرید.
2. کد را push کنید؛ ریلوی خودکار بیلد و دیپلوی می‌کند.
3. Volume سر جایش است؛ کلیدها و کاربران می‌مانند.
4. اگر نسخهٔ باینری‌ها را بالا برده‌اید، از تب **هسته‌ها** هر کدام را ری‌استارت کنید.

> نکته: پورت‌های داخلی اینباندها (۱۱۰۰۰ به بالا) با تغییر کانفیگ ممکن است بازتخصیص پیدا کنند؛ این طبیعی است و در لینک‌ها اثری ندارد (لینک‌ها بر اساس پورت عمومی ساخته می‌شوند).

## محدودیت‌های بستر

| محدودیت | اثر | جبران |
| :--- | :--- | :--- |
| فقط یک TCP Proxy | نمی‌توانید یک پورت مخصوص MTProto و یکی مخصوص REALITY داشته باشید | مالتی‌پلکسر تک‌پورت (`src/proxy/mux.js`) |
| بدون UDP عمومی | Hysteria2 / TUIC / WireGuard کار نمی‌کنند | از Xray TCP-based استفاده کنید یا نود جدا بگیرید |
| TLS لبه مال ریلوی است | کانفیگ‌های WS گواهی معتبر دارند، کانفیگ‌های TCP/TLS گواهی خودامضا | REALITY را برای TCP ترجیح دهید |
| IP مشترک ریلوی | ممکن است بعضی سرویس‌ها به آن حساس باشند | دامنه/ProxyIP یا نود دیگر |
| ساعت اجرای رایگان | سرویس بعد از مدتی خواب/محدود می‌شود | پلن Hobby یا پینگ دوره‌ای `/health` |

## عیب‌یابی سریع

```bash
curl -s https://<domain>/health
curl -s https://<domain>/api/bootstrap | head -c 400
```

- `{"ok":true}` یعنی پنل زنده است.
- اگر `/api/state` بعد از ورود خالی است، لاگ دیپلوی را ببینید؛ خطاهای `[boot]` یا `[mux]` را جست‌وجو کنید.
- کارت هسته‌ها در پنل، خروجی واقعی `xray -test` و `sing-box check` را در `lastError` نشان می‌دهد.

## بیلد و دانلود باینری‌ها

ایمیج سه باینری را در زمان بیلد از GitHub می‌گیرد: `xray`، `sing-box` و `mtg`.

- هر دانلود با `--retry` و تا **۵ تلاش** (با تأخیر پلکاني) تکرار می‌شود؛ خطای `502/503/504` از CDN گیت‌هاب معمولاً در تلاش دوم حل می‌شود.
- اگر شبکهٔ بیلد به GitHub دسترسی ندارد، در **Settings → Build → Build Args** این را اضافه کنید:

  | نام | مقدار نمونه |
  | :--- | :--- |
  | `GH_MIRROR` | `https://gh-proxy.com/` |

  آینه به ابتدای آدرس کامل چسبانده می‌شود: `https://gh-proxy.com/https://github.com/...`
- اگر `mtg` دانلود نشود، بیلد **موفق** می‌ماند و پنل با پیام «باینری موجود نیست» فقط MTProto را خاموش نشان می‌دهد؛ `xray` و `sing-box` اگر نیایند بیلد را متوقف می‌کنند.
- **پایهٔ ایمیج `node:22-bookworm-slim` است، نه Alpine.** باینری رسمی sing-box داینامیک و وابسته به glibc است؛ روی Alpine خطای `/app/bin/sing-box: not found` (exit 127) می‌دهد. xray و mtg استاتیک‌اند.
- برای بیلد محلی: `docker build -t nightline .` و سپس `docker run -p 8080:8080 -p 8443:8443 -v $PWD/data:/data nightline`.

## نقشهٔ پورت‌ها و خطاهای رایج شبکه

| پورت | سرویس | تنظیم Railway |
| :--- | :--- | :--- |
| `8080` | پنل + API + صفحهٔ اشتراک | Public Networking → دامنهٔ HTTPS → **Target Port: 8080** |
| `8443` | مالتی‌پلکسر TCP | TCP Proxy → **Target Port: 8443** |

پنل روی چند پورت گوش می‌دهد (`NL_PANEL_PORT`، `PORT`، `8080`، `3000`) تا هر پورتی که دامنه هدف بگیرد پاسخ بگیرد.

- **`[mux] listen EADDRINUSE 0.0.0.0:8443`** یعنی `PORT` و `NL_TCP_PORT` یکی هستند. مالتی‌پلکسر پورت `8443` را نگه می‌دارد و پنل به `8080` می‌رود؛ بهترین کار: `PORT=8080`.
- **`502 Bad Gateway`** یعنی دامنهٔ HTTPS به پورتی می‌زند که چیزی آنجا نیست. Target Port دامنه را `8080` بگذارید.
- درخواست HTTP که به پورت `8443` (مالتی‌پلکسر) برسد، به پنل هدایت می‌شود؛ پس اگر دامنه را اشتباهاً روی `8443` گذاشته‌اید هم پنل باز می‌شود، ولی مسیر درست همان `8080` است.
